# AML — AI Development Playbook

How code gets written on this project. Every AI coding session (Claude Code or otherwise) reads `CLAUDE.md`, which points here. The purpose of this document is to make AI-generated code *predictable*: same structure, same tests, same documentation, every time.

## 1. Principles

1. **Files are the truth, in canonical form.** Notes are saved as canonical AML markdown (ADR-003); nothing the parser doesn't model may be dropped — it becomes a Raw node and is written back verbatim. If a feature needs data the file can't hold, it goes in front matter, a manifest, or `.aml/`, in that order.
2. **One work package per session.** Each WP in the plan is sized to be specified, built, tested and documented in a single focused session (roughly 2–6 hours of agent time). If a WP won't fit, split it *before* starting.
3. **Spec before code.** Every WP has a spec file `docs/specs/WP-x.y-<slug>.md` written *first* (template below). The spec is the prompt.
4. **Tests are the memory.** AI sessions do not remember previous sessions; the test suite does. Regressions in the golden corpus or e2e suite block merge.
5. **Boring dependencies.** Prefer libraries with large, stable public documentation. Pin versions. No dependency added without a line in the spec explaining why.
6. **Thin Rust, typed edge.** Rust does I/O (local and SMB), indexing, sidecars. Everything else is TypeScript. The boundary is generated by tauri-specta; hand-written IPC types are forbidden.
7. **Small modules, explicit interfaces.** Max ~300 lines per file; feature folders (`src/features/<feature>/`) own their state, components and tests.
8. **Docs move with code.** A WP is not done until `ARCHITECTURE.md`, the feature's README, and the CHANGELOG are updated in the same PR.

## 2. Repository layout (Stage 0 creates this)

```
AML/
  CLAUDE.md                  ← entry point for every AI session
  README.md
  docs/
    brief/                   ← original brief (this file's origin)
    00-OPEN-QUESTIONS.md
    01-DEVELOPMENT-PLAN.md
    02-ARCHITECTURE-DECISIONS.md
    03-GLOSSARY-AND-NAMING.md
    04-AI-DEVELOPMENT-PLAYBOOK.md
    05-UX-ALTERNATIVES.md
    ARCHITECTURE.md          ← living map: modules, data flow, IPC commands
    specs/                   ← one spec per WP
    qa/                      ← manual test scripts, one per stage
    CHANGELOG.md
  src/                       ← React/TS
    app/                     ← shell, routing, layout, theming
    features/<feature>/      ← editor, folio, search, history, compile, …
    lib/                     ← shared utils (markdown parsing, front matter)
    ipc/                     ← generated bindings (do not edit)
  src-tauri/                 ← Rust
    src/commands/<domain>.rs
    src/index/ src/history/ src/sidecar/ src/watch/
    sidecars/                ← pandoc, typst binaries per target
  themes/                    ← app CSS themes
  book-designs/              ← Typst templates
  test-corpus/               ← round-trip markdown files + expected canonical output
  e2e/                       ← Playwright specs
  .github/workflows/         ← ci.yml (mac+win), release.yml
```

## 3. Work-package spec template

```markdown
# WP-x.y — <Title>
**Stage:** x · **Depends on:** WP-… · **ADRs:** ADR-… · **Estimated sessions:** 1

## Goal
One paragraph. What the user can do after this WP that they couldn't before.

## Scope
- In: …
- Out (explicitly): …

## Design
- Data: files/front matter/manifests touched
- IPC: commands added (name, args, return) — Rust signatures
- UI: components, states, keyboard shortcuts, empty/error states
- Edge cases: (external file change mid-edit, unicode, 0-byte file, 200 MB PDF…)

## Acceptance criteria
- [ ] AC1 … (user-observable, testable)
- [ ] AC2 …

## Tests
- Unit: …
- Round-trip corpus additions: …
- E2E: …
- Manual QA script: docs/qa/stage-x.md § y

## Docs to update
ARCHITECTURE.md § …, feature README, CHANGELOG, glossary if any new term
```

## 4. Definition of Done (checked by the human at each WP)

- [ ] Spec exists and acceptance criteria are all ticked with evidence (test name or screenshot)
- [ ] `pnpm check` passes: typecheck, Biome, Vitest, `cargo clippy -D warnings`, `cargo test`
- [ ] Round-trip corpus green (or intentionally updated with a note in the PR)
- [ ] E2E suite green on macOS and Windows CI
- [ ] Manual QA script for the WP executed by you on at least one OS; results recorded in `docs/qa/results/YYYY-MM-DD-WP-x.y.md`
- [ ] No new dependency without justification; `pnpm audit` / `cargo audit` clean
- [ ] Docs updated; CHANGELOG entry written; screenshots refreshed if UI changed
- [ ] Performance budget respected (see §6)

## 5. Session protocol (paste at the start of each AI session)

```
Read CLAUDE.md, docs/ARCHITECTURE.md, docs/03-GLOSSARY-AND-NAMING.md and docs/specs/WP-x.y-*.md.
Restate the acceptance criteria in your own words and list any ambiguity BEFORE writing code.
Work in a branch wp/x.y-<slug>. Commit in small steps with messages "WP-x.y: <what>".
Run `pnpm check` before claiming completion. Update docs listed in the spec.
Finish with a summary: what was built, what was NOT, test results verbatim, follow-ups.
```

## 6. Quality gates & budgets

| Gate | Tool | Threshold |
|---|---|---|
| Type safety | `tsc --noEmit`, `cargo check` | 0 errors |
| Lint/format | Biome, clippy | 0 warnings |
| Unit coverage | Vitest | ≥ 80 % on `src/lib` and `src/features/*/model` |
| Fidelity | round-trip corpus | parse→serialise→parse AST-equal; second serialise byte-identical (idempotent); Raw nodes verbatim |
| E2E | Playwright | all green, both OSes |
| Cold start | manual/CI timer | < 1.5 s to editor on a 2k-note Folio |
| Typing latency | e2e perf test | < 16 ms keystroke-to-paint on 50k-word note |
| Index rebuild | Rust bench | < 5 s for 5k notes / 50 MB |
| Installer size | CI | < 90 MB per OS (including Pandoc, Typst, Syncthing) |
| Memory | manual | < 400 MB with 20 notes open |

## 7. Common AI failure modes to guard against (turn into tests)

- Serialiser drops or mangles syntax it doesn't model (HTML blocks, callouts, nested lists in blockquotes) → round-trip corpus with Raw-node cases.
- Serialiser is not idempotent (each save changes the file again) → idempotence test.
- Position mapping errors after unicode/emoji (spell-check underlines, find/replace) → corpus includes CJK, emoji, combining marks, RTL.
- Leaving the Syncthing sidecar orphaned on crash/quit, or clashing on its port → lifecycle tests; unique port per Folio; PID file check on launch.
- Blocking the UI thread with indexing → e2e asserts responsiveness during rebuild.
- Path handling that breaks on Windows (`\`, drive letters, reserved names, case-insensitivity) → path util with tests; CI on Windows.
- Silent catch blocks → lint rule: no empty catch; errors surface in a global toast + log.
- Inventing IPC commands that don't exist → generated bindings only.
- Regressing keyboard shortcuts → shortcut registry is a single table with an e2e test that presses each.

## 8. Release process (Stage 8 sets up)

Tag → CI builds signed `.dmg` (notarised) and `.msi`/`.exe` → GitHub Release → in-app updater (`tauri-plugin-updater`) checks the release feed. Manual channel for you only; no telemetry.
